# Blit — full QA & UX review

*2026-09-26 · repo at commit `5c5d5d5` (clean tree, untouched by this review)*

**How this review was run.** Twelve static reviewers (one per risk dimension), every finding then adversarially verified by independent agents told to *refute* it (data-loss/wrong-result claims got two verifiers with different lenses; the rest were group-verified); 98 raw findings, 96 survived, 2 were refuted and are excluded. In parallel: the Debug app build, the full BlitKit test suite (all green), the in-app right-click/rename harness, the pixel-art render harness, and hands-on CLI engine experiments on a throwaway APFS disk image (verified copy, collisions, `--overwrite`, kill ‑9 mid-copy, resume, empty files, symlink cycles, exit codes). Where a claim was testable in isolation, verifiers extracted the code and ran it standalone (`swiftc`); several findings below were *empirically reproduced*, not just read. No server or NAS was written to; no credentials were touched.

**Headline.** The core engine is genuinely strong — the promise "nothing is marked done without a SHA-256 match" holds on the happy path and in most crash cases, and the move ledger correctly refuses to delete skipped/size-only/failed sources. The serious problems cluster in four places: **(1)** a path-traversal hole in the filename policy, **(2)** error paths that silently *downgrade* verification instead of failing (and moves then delete sources on the downgraded check), **(3)** the retry/failure model misclassifying advisories and spec'd-recoverable cases, and **(4)** pane-focus/UI-state bugs that can aim destructive actions at the wrong files. Several PRD requirements (R1.1 key auth, R1.2 shell endpoint, R5.2 pause/cancel, R5.3 conflict rules, R5.8 download preflight, much of R2.3/R2.10 drag-and-drop) are not implemented.

## 1 · Findings — most severe first

### 1.1 Data loss / integrity

**F1. Server-supplied filenames are never checked for `/` — path traversal writes outside the download folder** — `BlitKit/Sources/BlitRemote/Transfer.swift:58` *(security-critical; also R3.10 violation)*
A hostile or compromised SFTP server can return a READDIR entry named e.g. `x/../../../Users/<you>/Library/LaunchAgents/evil.plist` (any bytes are legal in the wire filename; `SFTPClient.list` filters only literal `.` and `..`, `SFTPClient.swift:171`). `TransferPlan.localName` keeps valid UTF-8 verbatim, `remoteFiles` concatenates it into `relativePath`, and `download()` creates intermediate directories and renames the file into place — an arbitrary user-writable path, reachable from the GUI download path (`TransferManager.swift:695/709`). With `--overwrite` it replaces existing files. Verifiers reproduced `localName` passing traversal names through verbatim (standalone `swiftc`), and noted the leading-dot filter only stops payloads that *begin* with `.`.
*Fix:* percent-escape `/` (0x2F) in `localName`, and reject `.`/`..` components when building `relativePath`. *Confidence: high — confirmed by 2 adversarial verifiers.*

**F2. Any interrupted/errored NAS-side hash silently downgrades to SMB read-back — and a move then deletes the source** — `BlitKit/Sources/BlitLocal/LocalCopy.swift:286-295` + `Blit/Model/TransferManager.swift:43-49`
`verify()` rethrows only `CopyMismatch`; *every other* error from the NAS hasher — including `SSHError.disconnected("the hash was interrupted")`, the exact class commit `be9f51d` taught the download path to treat as fatal — falls back to read-back over SMB, which R4.2 itself says can be answered from the Mac's page cache. The file is logged `✓ SHA256 … READ-BACK`, `VerifiedSources` records `.readBack` as delete-eligible, and `removeVerifiedSources` deletes the SSD source. One dropped SSH connection during a move + NAS-side corruption = the only good copy deleted, "verified" without its at-rest bytes ever being read. (Quitting Blit mid-copy can trigger this too: `prepareForQuit` closes the NAS connection while the copy loop finishes.)
*Fix:* mirror the download path — fall back only on `RemoteHasher.Unavailable`, rethrow interruptions so the file retries; and consider requiring `.nas` (not `.readBack`) before a move may delete a source. *Confidence: high (both verifiers confirmed; mechanism traced end-to-end).*

**F3. Move sources are deleted at batch end with no freshness re-check** — `Blit/Model/TransferManager.swift:726` (remote) and `:752` (local)
The ledger stores only paths — no size/mtime — and removal runs once, after the *whole batch*. During a multi-hour move, a source rewritten in the meantime (torrent client re-check, another app) is deleted at whatever state it's in; locally `fm.removeItem` on a path that became a folder deletes it recursively. The engine's changed-on-server check covers only up to hash time.
*Fix:* record size/mtime at verification time in `VerifiedSources` and re-stat before each removal, skipping (with a KEPT note) on mismatch — or remove each source immediately after its own file verifies to shrink the window. *Confidence: medium (mechanics certain, window requires a concurrent writer).*

**F4. No local source-stability gate: a still-being-written file copies torn, "verifies", and a move deletes it** — `BlitKit/Sources/BlitLocal/StreamCopy.swift:50`
StreamCopy fstats once and reads to EOF; source size/mtime are never re-checked. On the read-back path the copy is compared only against the hash of the bytes that were streamed (no size check against the listing — unlike download finalize), so a truncated capture self-matches and the still-growing source is deleted on a move. The NAS-hash path incidentally catches size *growth*; same-size in-place rewrites slip past both. R3.9 gives remote downloads exactly this gate; the local engine has none.
*Fix:* fstat the source after the copy and fail the file if size/mtime changed since listing; size-check the part against `file.size` on the read-back path. *Confidence: high.*

**F5. Verification failures on servers that CAN hash are classed "Unavailable" → files accepted size-only** — `BlitKit/Sources/BlitRemote/Transfer.swift:249-253`
R4.1 permits the size-only fallback only when the server *genuinely can't hash*. But any plain-fallback failure with an exit status becomes `Unavailable`: a chrooted SFTP endpoint whose shell sees different path roots (the README's own benchmark finding 6 — nothing ever sets `mapPath` on the download path), an unreadable file, a `.bashrc` that pollutes stdout. Every file in the batch is then renamed final on the vacuous size check. The verifiers' correction is important: this is *not* silent (files are labeled size-only, and moves never delete size-only sources) — but a corrupt download is still renamed final and counted finished without byte verification, on servers that can hash. Core-promise violation in the false-accept direction.
*Fix:* reserve `Unavailable` for `channelRequestRefused` and exit 126/127 of the plain run; treat every other failure as a per-file verification failure that keeps the `.blitpart` and retries. *Confidence: high.*

**F6. Power-loss ordering: `.blitpart.state` can record ranges whose bytes never hit disk; size-only servers then accept zero-filled holes** — `BlitKit/Sources/BlitRemote/Transfer.swift:375-377, 628-633` + `PartFile.swift:23`
Range state is saved right after `pwrite` returns; the only `sync()` is in finalize, and the state JSON isn't fsynced either. After power loss / kernel panic, resume trusts `state.done` and skips a hole. With server hashing the SHA-256 catches it (cost: a full re-download). Without it (`.sizeOnly`), finalize's size check compares the *preallocated* part file's size — always equal by construction (`PartFile.create` ftruncates to full size) — so a file with a zero-filled 256 MB hole is renamed final and logged `✓ SIZE ONLY`. (I independently found and verified this before the workflow's reviewer did — two independent traces agree. App-crash-only is safe: the download future completes only when `pendingWrites == 0`.)
*Fix:* fsync the part before each state save (or store per-range checksums in `PartState`; or refuse to resume when the only verification would be size-only). *Confidence: medium-high (mechanics certain; needs power loss, not app crash).*

**F7. Mid-batch destination collisions are silently overwritten at finalize** — `BlitKit/Sources/BlitLocal/LocalCopy.swift:253`, `BlitKit/Sources/BlitRemote/Transfer.swift:638`
The exists/skip/fail decision runs once at plan time; hours later, `rename(part, final)` atomically replaces whatever now sits at the final path — no check, no log — despite the app's effective rule being "skip if present". Another machine writing into the same NAS folder during a long batch loses its file.
*Fix:* re-check existence immediately before rename (`renamex_np` + `RENAME_EXCL` on APFS; stat-then-rename to narrow the window on SMB). *Confidence: low likelihood, mechanics certain.*

**F8. Remote rename/move guard is stat-then-rename, and `try?` treats *any* stat failure as "target missing"** — `Blit/Model/FileOperations.swift:349`
On servers whose `SSH_FXP_RENAME` replaces targets (SFTPGo does; OpenSSH doesn't), a file created in the ~1 RTT window is silently replaced. Worse per the verifiers: a permission-denied or transient stat error defeats the guard *entirely* — no concurrent writer needed.
*Fix:* proceed only on a definite `noSuchFile` status; accept (and document) the residual TOCTOU that SFTP v3 can't close. *Confidence: medium.*

**F9. The verified badge survives an unverified rewrite of the same path, still claiming "SHA-256 matched"** — `Blit/Model/VerifiedIndex.swift:48-53`
Delete a verified file in Blit (delete paths never clear the index), re-download it from a no-shell endpoint (size-only): `apply()` keeps the old entry, sizes match, and the badge's hover says "SHA-256 matched the server's · <old date>" for bytes that were never hashed. Persists across launches because `load()` replays the whole historical log. *Empirically reproduced with the extracted logic in a standalone test.*
*Fix:* clear entries when a `result=="ok"` record rewrites a path with method size-only/none, and from delete/trash paths. *Confidence: high.*

### 1.2 Wrong results

**F10. The R1.7 Wi-Fi warning is appended to `job.failures`, so a fully verified copy retries five times and ends FAILED** — `Blit/Model/TransferManager.swift:811`
The exact situation R1.7 was written for (NAS routed over Wi-Fi while wired is up) now: warns, copies and verifies everything, then burns ~8.7 minutes of retries (files all "already present" → no progress → `stalled` hits 5) and ends `✕ GAVE UP AFTER 5 ATTEMPTS`, red HUD, "1 problem" notification, no Dock checkmark. Three reviewers found this independently; a standalone test confirmed the string is classed retryable.
*Fix:* make it a note/advisory flag, not a failure. *Confidence: high.*

**F11. HUD and strip claim "SERVER SHA256" / "NAS SHA256" even when every file fell back to weaker verification — and `✓` prefixes "SIZE ONLY"** — `Blit/Model/TransferManager.swift:180-184, 916-917, 959-961`
`verificationMethod` is static per job kind (NAS variant depends only on whether the NAS login *connected at start*). A no-shell download shows "VERIFYING · SERVER SHA256" for files finishing `.sizeOnly`; a NAS copy that downgraded to read-back keeps saying NAS SHA256, and the app drops the `.readBack(reason:)` the CLI prints. The durable TransferLog is honest — the live surfaces aren't. README:120: "a checkmark means verified"; the log line prints `✓ SIZE ONLY`.
*Fix:* derive the label from observed per-file outcomes; non-checkmark glyph for size-only/none. *Confidence: high.*

**F12. R1.2's separate shell endpoint doesn't exist — SFTPGo-style setups silently lose SHA-256 verification forever** — `Blit/Model/ServerStore.swift:9` (no fields), `TransferManager.swift:703`
`mapPath` exists in the engine but nothing sets it on the download path, and `ServerConfig`/the editor have no shell host/port/root. Anyone on the provider's default SFTPGo endpoint runs the whole 27–30 TB/month workflow size-only, with only per-file labels (see F11) to notice it by.
*Fix:* add shell endpoint + path-root mapping to `ServerConfig` and the editor; wire `RemoteHasher` to it. *Confidence: high.*

**F13. The server hash script caches the hash of a *partial* stream when `dd` fails, permanently poisoning the cache** — `BlitKit/Sources/BlitRemote/Transfer.swift:211-216`
`h=$(dd if="$p" … | sha256sum | cut -c1-64)` ignores dd's exit status (no pipefail in POSIX sh); an EIO/EACCES mid-read yields a valid-looking 64-hex hash of the truncated stream, cached under path|size|mtime. Every retry then gets the same wrong hash as `cached`; nothing ever invalidates on mismatch → an endless mismatch/re-download cycle (see F15) until someone deletes `~/.cache/blit/sha256/<key>` on the server by hand. *Empirically reproduced by running the exact script text against an unreadable file: run 1 cached the empty-input hash, run 2 served it back as `cached`.* Fails safe (never a false accept) but blocks completion at 27–30 TB/month scale.
*Fix:* propagate dd's status / compare byte count before caching; delete the server cache entry for a path whose verification mismatched before retrying. *Confidence: high.*

**F14. Hash cache keyed by whole-second mtime can serve a stale hash for an mtime-preserving re-upload; no invalidation on mismatch** — `Transfer.swift:205-208, 614-624`
Same-size replacement uploaded with rsync `-t`-style mtime preservation → old hash served as `cached` forever; the good download can never verify. Never a false accept. *Confidence: low practical likelihood; mechanism certain.*

**F15. A persistent SHA-256 mismatch re-downloads the whole file in an unbounded loop** — `Blit/Model/TransferManager.swift:556` + `Transfer.swift:621-624`
Mismatch deletes the resume state (correct — don't resume wrong bytes) so every retry re-downloads *from scratch*, makes byte progress, resets the `stalled` counter, and never trips the give-up-after-5 rule. Combined with F13/F14 this is an infinite multi-GB loop on a 148 ms link. R4.3 says re-download — but bounded.
*Fix:* count verification mismatches per file and fail permanently after N (2–3), keeping the `.blitpart`. *Confidence: high.*

**F16. R3.9 violated: "changed since it was listed" is a *permanent* failure, never a re-list** — `Transfer.swift:536-539` + `TransferManager.swift:500`
The PRD says explicitly: re-list, don't treat as corruption. The marker list classes it permanent; the job fails with no retry. Bonus: `begin()` runs before the stability gate, so a full-size preallocated `.blitpart` (50 GB for a big video) is left behind for every still-being-written file.
*Fix:* re-stat/requeue with new size/mtime on gate failure; delete the fresh part/state; order `begin()` after the gate. *Confidence: high.*

**F17. A stale listing flips a Trash-eligible delete to the permanent-delete path** — `Blit/Model/FileOperations.swift:258`
`canTrash` treats an unreadable/vanished item as not-trashable (`allSatisfy` fails), so ⌘⌫ on a 5-file SSD selection containing one file Finder already moved shows "Delete 5 items permanently?" and uses `removeItem` — bypassing the Trash the PRD promises for local drives. *Mechanism proven in a standalone test.*
*Fix:* skip missing items in `canTrash` / resolve trashability from the parent volume. *Confidence: high.*

**F18. Destructive commands target the click-activated pane, not the keyboard-focused one** — `Blit/Views/ContentView.swift:274, 291-294`
Pane activation flips only on primary-click tap gestures. Right-click in pane B (menu opens there — it *looks* active), dismiss, press ⌘⌫: pane A's selection is deleted — and for trashable local files there's *no dialog at all*. Tab-focus traversal diverges the same way, as do ⌘X/⌘C/Space. Verifiers found a clicks-only repro (click pane B's table, then pane A's non-focusable header).
*Fix:* drive activation from real key-view focus (`@FocusState` per Table / first-responder observation), not tap gestures. *Confidence: high.*

**F19. Multi-window: Space/↑↓/Return act on another window's browser** — `Blit/BlitApp.swift:32` + statics in `BrowserModel+QuickLook.swift:16-17`
`BrowserModel.active`/`activeWindow` are process-wide statics set at view start and by `updateNSView` re-renders; File → New Window is not disabled. Space in window 1 can Quick Look window 2's selection, Return renames the other window's file, or keys go dead (and closing window 2 kills Space everywhere).
*Fix:* resolve the browser from the key window at event time; update on `didBecomeKey`. *Confidence: medium.*

**F20. Recursive local copies silently drop symlinks and empty folders; the job reports clean success** — `BlitKit/Sources/BlitLocal/LocalCopy.swift:34`
`localFiles` keeps only `isRegularFile`; links are neither followed nor recreated, empty dirs never created; counts reflect the reduced set so nothing warns. Violates R3.1. On a move, source folders holding links are left behind (the removal's non-empty check saves the data — confirmed). *Corroborated twice: standalone test of `localFiles`, and my own CLI experiment (symlink cycle + absolute link: both vanished from the copy, exit 0).*
*Fix:* recreate links (or emit per-item skipped events); create empty dirs from the walk. *Confidence: high.*

**F21. Failed source removals don't fail the move job — and the summary mislabels the kept files** — `Blit/Model/TransferManager.swift:730, 768, 776`
Removal errors are log notes only: the job ends `.finished`, the notification says "N of N verified" as clean success while zero sources were removed, and the summary line calls the kept files "NOT VERIFIED BY SHA256" — factually wrong (they verified; deletion failed).
*Fix:* append removal failures to `job.failures` (or a kept-count in the notification); split "removal failed" from "not verified". *Confidence: high.*

**F22. The Dock's pixel checkmark shows for batches that weren't verified or contained a failed job** — `Blit/Model/TransferManager.swift:490`
`finish(verified:)` is computed from the *last* job only; an all-size-only or all-already-present batch (or fail-then-succeed pair) gets the "finished verified" checkmark README:147 reserves for verified batches.
*Fix:* compute over all jobs in the drained batch, requiring actual verification coverage. *Confidence: high.*

**F23. A dead browse session shows "connected" in the sidebar forever** — `Blit/Model/ConnectionManager.swift:73`
Keep-alive's guard returns silently when the channel is already inactive: state stays `.connected`, signal bars stay lit (README:154), the dead client stays cached, keep-alive ends permanently, and nothing reopens in the background — until the next user action happens to touch `browseClient`. *Confidence: high.*

**F24. `disconnect()` ignores an in-flight connect: stale-config sessions install after Edit/Remove Server** — `Blit/Model/ConnectionManager.swift:104-123`
Edit or remove a server while its connect attempt is pending (up to ~40 s window): the old-config client is installed unconditionally afterwards — browsing silently uses the old host/credentials, or an orphaned connection + keep-alive pings the server for the app's lifetime. The post-edit `reload()` can even *join* the stale attempt.
*Fix:* cancel/invalidate `inFlight` in `disconnect()`; re-check currency before installing. *Confidence: medium.*
